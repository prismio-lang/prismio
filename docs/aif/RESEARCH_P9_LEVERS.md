# Research prompt 9: memory-model levers C++ and Rust are forbidden

Written 2026-11-22, as an answer to prompt 9 of `RESEARCH_BRIEF.md`. It uses the test from
`docs/STRUCTURAL_LEVERS_PLAN.md` §0: a lever counts only if a rule in C++'s or Rust's language or
library definition forbids it, not merely if their compilers don't do it. That plan's audit
(2026-11-11) covers the general levers: float reductions (built), element width and container
representation (both closed), compressed references (unmeasured) and devirtualisation. This note
covers only the **memory-model** levers, and measures each one before ranking it.

Nothing here is built. The probes ran on an Apple M5, on battery, with medians of 15 process
runs. Their sources were in this session's scratchpad and are not kept. Each probe is described
well enough to rewrite.

## 0 · The two rules that make these levers possible

Both rules were checked against the tree.

1. **A release is never observable.** Prismio has no user-written destructors: no `Drop` trait and
   no `deinit`. Release functions are generated by the compiler, and on hosted targets they free
   through the runtime's own seam. The one exception is freestanding and kernel programs, where
   the program supplies `prismio_alloc` and `prismio_free`. In C++, a destructor is user code, and
   `operator delete` can be replaced by the program. In Rust, `Drop` is user code and runs at scope
   end in a documented order, and `#[global_allocator]` can be replaced. Both languages therefore
   have to run every release at exactly the point where the language places it.
2. **An address is not observable in safe code.** The only ways to get an address are
   `std.raw.addressOf` and FFI. A view such as `let n = v[i]` is a provenance edge the compiler
   tracks, not a number the program holds. Layout already vetoes types that reach FFI or
   `std.raw`. In C++ and Rust, pointer width, `sizeof`/`size_of`, round trips through `uintptr_t`
   and the stability of element addresses are all part of the contract.

## 2 · Lever 1: teardown at exit, and releasing at last use

**Probe.** `struct T { value: Int, left: T?, right: T? }`, a depth-21 tree built by a function
that returns it, which makes it T2 on the heap (`prismio aif` confirms), then summed. Arm A returns
from `main`, which emits `__aif_release_T` on the tree. Arm B calls `exit(s % 256)` instead, and
the IR shows no release. The C++ arm uses `unique_ptr`, with and without `std::exit`.

| Arm | Prismio | C++ |
|---|---:|---:|
| return from `main` (full teardown) | 19.2 ms | 46.2 ms |
| `exit` before teardown | 13.6 ms | 29.5 ms |
| ratio | **0.70×** | 0.64× |

**Mechanism.** In a hosted build without `--verify`, a normal return from `main` skips the scope
drops of `main`'s own bindings, the same way `exit` already does. Buffered output still has to be
flushed; `exit` already handles that. Keep teardown in three cases: under `--verify` (the ledger
needs it), when the slab is off (`PRISMIO_SLAB=0`, so leak checkers stay quiet), and on
freestanding or kernel targets, where the program supplies `prismio_free` and a release is
observable.

**Soundness.** Skipping the release can only cause a leak, and the operating system reclaims it at
exit. No other code runs after `main` returns. Tasks still running end with the process, as they do
today.

**1b · releasing at last use.** C++ and Rust release at the end of the scope. Prismio may release a
T2 value right after its last use, which lowers peak memory. Swift's optimiser already shortens
lifetimes this way (that is why `withExtendedLifetime` exists). Automatic arenas already have
non-lexical extents; this extends the same idea to T2 drops. The prize is not yet measured. The
benchmark to settle it is peak RSS on `graph_churn_full`.

**A consequence for the brief.** In a batch program, any memory still live when the process exits
costs nothing to leave. The compiler's 1,052 `rc:none` sites (brief §4.1) are therefore a problem
only for long-running processes such as the language server. Prompt 1 should rank its mechanisms
for that case.

**Benchmark.** `tree_build_exit`: build N nodes, traverse, return from `main`, at N = 2^16, 2^21 and
2^24, with an idiomatic C++ arm (`unique_ptr`) and a Rust arm (`Option<Box>`). Say in the record
that an expert C++ programmer could call `std::exit`; the lever is that Prismio's compiler does it
without being asked.

## 3 · Lever 2: inline capacity and an embedded Vec header

**Where `graph_churn`'s memory goes** (`benchmarks/hosted/prismio/graph_churn.psm`).
`ChurnNode { value: Int, live: Int, edges: Vec<Int> }`, where each node has 1 to 6 edges.

- Prismio: the node is its own 16-byte allocation, because a struct that holds a `Vec` is not flat,
  so `Vec<ChurnNode>` stores pointers. On top of that, the edge list is a fused `RtList`: a 64-byte
  header plus 4–24 bytes of elements, rounded up to an 80-byte slab class. That is **96 B in 2
  allocations per node.**
- C++: the node sits inline in `vector<ChurnNode>`, taking 32 B with its 24-byte `vector` header,
  plus a 16-byte heap block for the edges. That is **48 B in 1 allocation per node.**

The arithmetic matches the latest suite run: peak memory 1.35–1.46× C++ on the four `graph_churn`
arms, and about 1.68M allocations against C++'s ~0.8M (ALLOCATOR_PLAN).

**Two steps. The first closes a gap; the second is the lever.**

1. *Gap: a 64-byte header.* `RtList` holds `data`, `len`, `cap`, `elem_own`, `elem_release`,
   `arena`, `elem_size`, `grave`, `grave_len`, `grave_cap` and `fused`. Of these, `elem_own`,
   `elem_release` and `elem_size` are known statically at each call site (the runtime comment
   at `lang_runtime.c:2538` already makes this argument for the inline entry points). `grave` is
   needed only for parking, and `arena` only for an arena-served Vec. A 16-byte hot header (data,
   len, cap) with a cold record allocated on demand is ordinary engineering, not a lever. It would
   bring a node to 16 + 32 B. A second gap is that non-flat structs are never stored inline in a
   Vec; `Vec<String>` already stores its pairs inline, so owning elements stored inline exist as a
   precedent.
2. *Lever: embed the header and K elements in the parent.* The fused representation already makes
   `data` a pointer into the same block, so the runtime's list functions don't care where the
   elements live. Embedding goes one level up: the header and K inline slots live inside the
   parent's field, and `data` points into them until the list grows past K and moves out to the
   heap. That makes a `graph_churn` node 48 B with **no** allocation of its own, which is fewer
   allocations than C++.

**Soundness.** An embedded Vec must never leave its field as a whole: no `sink` or return of
`node.edges`, and no binding of it that outlives the parent. Otherwise its interior `data` pointer
would dangle, or the parent's release would free a block that was never allocated. That is exactly
what the closed-column proof (`src/ir/columns.psm`) already establishes for a private `Vec` field:
every use is a list builtin through the field. Assigning a new Vec to the field
(`nodes[u].edges = Vec.withCapacity(0)`) resets the slots in place and releases any spilled heap
buffer. The parent's release has to release the spilled buffer and never the embedded block.

**Choosing K.** The static evidence here is `withCapacity(degree)` with `degree` bounded by
`1 + seed % 6`. In general, K should come from a measured distribution of lengths at drop time,
per allocation site. That needs the site-level telemetry of MEM-001, so MEM-001 is the
prerequisite.

**Benchmarks.** `graph_churn` as it is (its arms are fair: `vector<int>` and `Vec<i32>` inside the
node), plus a new `ast_children` benchmark: a tree whose `Vec<Node>` children have a skewed small
size distribution. Arms: idiomatic C++ (`std::vector`), Rust (`Vec`), and an expert C++ arm using a
small-vector type (`llvm::SmallVector` style) as the ceiling. The claim to test is that Prismio
reaches the expert arm without the programmer writing anything.

## 4 · Lever 3: 32-bit references relative to the slab

**Why it fits.** The slab reserves 64 GiB (`SLAB_RESERVE`) with a 16-byte grain (`SLAB_GRAIN`),
which is 2^36 / 2^4 = **2^32 grains**. A `u32` grain index therefore addresses the whole
reservation with nothing left over. Decoding a reference is `base + (index << 4)`, a single
AArch64 `add x, xbase, w, uxtw #4`. Grain 0 is reserved, so index 0 can mean `none`.

**Probe (C, bump allocation in one reserved range).** A 24-byte pointer node in a 32-byte class,
against a 12-byte compressed node in a 16-byte class. Second runs, with page faults warm:

| Depth (nodes) | Heap | Build | 5 traversals |
|---|---|---:|---:|
| 16 (64K, in cache) | 2 to 1 MB | parity | parity |
| 20 (1M) | 34 to 17 MB | 0.60× | 0.80× |
| 24 (16M) | 537 to 268 MB | 0.79× | 0.83× |

This matches the prior art: Lattner and Adve (MSP'05) report 20% to 2× faster and similar peak-heap
reductions on pointer-intensive programs; V8 reports about 40% of the heap; HotSpot uses the same
idea for its compressed object pointers.

**What blocks it, in the order to solve:**

1. **The target of every compressed field must be inside the reservation.** That rules out objects
   over 512 B, arena chunks, the libc fallback when the reservation is refused (under
   `vm.overcommit_memory=2`), Windows' recycler, and freestanding targets. Arenas and the large-block
   path would have to be carved from the same range, which is allocator stages 4–5. For a refused
   reservation, the choice is between failing at startup with a message (an environment failure,
   not an inference failure) and generating code for both layouts.
2. **Frame sites.** A `T?` field that may point at a stack value (brief §5 B) cannot be compressed.
   Veto those, or place such sites on the heap.
3. **Strings come later.** A literal or inline String does not point into the slab, so a String
   pair cannot shrink from 16 B to 8 B without a tag. Start with struct references (`T?` fields
   and Vec elements of struct type).

**The prize is outside the suite.** The benchmark arms run at about 2 MB of RSS, in cache, where
the probe reads parity. Add large-input arms instead: `tree_traversal` and `recursive_tree_rebuild`
at 2^24 nodes, and `trie_search` with a large vocabulary. Compare against idiomatic C++ and Rust,
and against an expert C++ arm that stores 32-bit indices into a node pool.

## 5 · Order

1. **Lever 1a.** About one codegen rule, with a measured 0.70× on build-then-exit workloads. Add
   the `tree_build_exit` benchmark in the same change.
2. **MEM-001 telemetry per allocation site.** Lever 2's K, lever 1b's prize and lever 4's copy
   volume all need it.
3. **Lever 2, step 1** (the 16-byte header; non-flat structs stored inline), measured on
   `graph_churn`'s memory. **Then step 2**, the embedded small Vec, behind the closed-column proof.
4. **Lever 3**, after allocator stages 4–5, with large-input arms written first.
5. **Lever 4**, folded into prompt 1's design for the `rc:none` residue. **Lever 5** waits until a
   workload asks for it.
