# Compile time — where it goes, and what it scales like

Measured 2026-08-17 on the session's host (Apple Silicon, macOS 26.5, Homebrew LLVM 22.1.8),
minimum of 3–5 runs per cell. Minimum rather than mean: the noise on this host is one-sided, and
the interleaving discipline from RESULTS-arena §6 is not needed for ratios this large.

Two compilers appear throughout:

| | |
|---|---|
| `L5` | the generation this session started from (2026-08-17, forced-layout session) |
| `R7` | this session's, with REQUIREMENTS 16 fixed and the toolchain object cache |
| `S3` | `R7` plus the bootstrap-script cache and the growable backend tables. Emitted IR identical to `R7` on all 89 programs, so §1–§3's frontend numbers are quoted against `R7` and stand |

## 1 · The frontend was quadratic in module size, and is now linear

`check` is parse + sema and nothing else, which is the phase REQUIREMENTS 16 named. The fixtures
are generated by a script that emits *N* functions each calling four earlier ones, so both the
number of declarations and the number of call sites grow with *N*.

| functions | bytes | `check` L5 | `check` R7 | speedup | emit-IR L5 | emit-IR R7 |
|---|---|---|---|---|---|---|
| 125 | 31 K | 0.019 | 0.016 | 1.2× | 0.024 | 0.021 |
| 250 | 58 K | 0.024 | 0.018 | 1.3× | 0.032 | 0.026 |
| 500 | 115 K | 0.043 | 0.023 | 1.9× | 0.056 | 0.036 |
| 1 000 | 228 K | 0.108 | 0.033 | 3.3× | 0.148 | 0.063 |
| 2 000 | 459 K | 0.357 | 0.051 | **7.0×** | 0.454 | 0.116 |
| 4 000 | 922 K | 1.241 | 0.088 | **14.1×** | — | 0.233 |
| 8 000 | 1.85 M | — | 0.169 | | — | 0.553 |
| the compiler | 518 K | 0.126 | 0.039 | 3.2× | 0.183 | 0.090 |

L5's per-doubling ratio over the last three rows is 3.3× then 3.8× — quadratic. R7's is 1.57×
then 1.73×, and once the ~12 ms fixed cost of starting a process and parsing `std/io.psm` is
subtracted it is 1.9× per doubling: **linear in module size** over a 60× range.

The two largest rows have no `L5` entry because that compiler could not build them at all:
`internal backend error: value table exhausted`. The value and block tables were fixed arrays
indexed by a counter that runs for the whole module, so their size was a ceiling on **program
size** — 65 536 SSA values, reached at about 3 500 functions. They grow now, the way every table in
`ir_symbols.c` does; the initial capacity is the old fixed size, so nothing below the old ceiling
allocates differently and **the IR is byte-identical on all 89 programs**. A 1.85 MB source
compiles.

### 1.1 What was actually quadratic

Four scans, in three passes, not the one the requirement named:

| where | scanned | once per |
|---|---|---|
| `semaFindFunctionOverload` | every top-level declaration | call site |
| `find_binding` (`ir_symbols.c`) | the binding table, whose floor was one `$fn$` entry per function | identifier — in sema **and** in codegen |
| `hasNamedTopLevel` (`main.psm`) | everything merged so far | merged declaration |
| `appendStatement` (`main.psm`) | to the end of the statement list | merged declaration |

A `sample` profile of L5 on the 8 000-function fixture puts 331 of 363 samples inside
`semaFindFunctionOverload` and `strcmp` beneath it, which is why that one was fixed first. The
other three are the reason a fixture with *no calls at all* was still superlinear (1 000 → 2 000
functions cost 2.56× on L5).

## 2 · The frontend is 4% of a cold build

Phase breakdown of one cold `prismio build` of the 505 KB synthetic project (2 200 functions,
3.34 MB of emitted IR), R7, total 3.31 s:

| phase | seconds | share |
|---|---|---|
| Prismio frontend: parse, sema, AIF, codegen, write `.ll` | 0.121 | 3.7% |
| `clang -O2 -c program.ll` | 2.508 | **75.8%** |
| compile the two runtime sources (`-O2`) | 0.203 | 6.1% |
| link | 0.181 | 5.5% |
| process startup, temp file IO, the rest | ~0.30 | 9% |

The same shape holds for a small program, where the fixed costs dominate instead: a 34-line
program builds in 0.44 s, of which the frontend is 0.015 s (3.4%) and the two runtime compiles
are 0.203 s (**46%**).

### 2.1 AIF's whole fixed point is 18 ms

`--debug` is a zero-round budget (SPEC §7.2), so the difference between a `--debug` build and a
release build is the entire inference engine — points-to, the facts, tiers, arenas, layout.

| | parse+sema | +codegen (`--debug`) | +inference (release) |
|---|---|---|---|
| the compiler, 518 KB | 0.035 | 0.075 | **0.0925** |

**The whole-program fixed point costs 18 ms on the largest real program in the tree** — 19% of the
frontend, 4% of an emit-IR run, and under 1% of a build. On the synthetic fixture it costs nothing
measurable, because that program has no allocations to solve for.

This is the number that decides what "incremental" has to mean here, and it is the opposite of
what was projected. AIF is not what makes a rebuild slow. LLVM is, exactly as it is for Rust, and
a summary cache keyed per INFERENCE §9 would be optimising 0.7% of the build.

## 3 · Cold and incremental

`aif/evidence/compile_bench.py` runs four scenarios per program, because they are four different
questions. Minimum of 3, fresh source copy and fresh cache directory per scenario.

| program | | cold | incremental | no-change | no-cache |
|---|---|---|---|---|---|
| 34-line program | `T3` | 0.521 | **0.178** | 0.176 | 0.535 |
| | `L5` | 0.539 | 0.535 | 0.534 | 0.543 |
| `g1_particles` | `T3` | 0.541 | **0.358** | 0.359 | 0.541 |
| | `L5` | 0.539 | 0.538 | 0.540 | 0.540 |
| synthetic 505 KB | `T3` | 3.065 | **2.702** | 2.692 | 2.985 |
| | `L5` | 3.243 | 3.376 | 3.249 | 3.295 |

**The `no-change` column is the finding.** Rebuilding with *nothing edited* costs the same as
rebuilding after a real edit — 0.176 against 0.178, 2.692 against 2.702. Nothing about the
program's own compilation is reused, at all. The cache reaches the toolchain and stops there, which
is why the win is 3.0× on a program whose build is mostly runtime and 1.10× on one where
`clang -O2` on 3.34 MB of emitted IR is 2.5 s of it.

So: **incremental builds are not done.** What is done is the half that is a pure function of the
toolchain, and on a small program that half was 46% of every build. The other half needs §5.

The one number that says whether this matters in practice: **the suite goes 226.3 s → 169.9 s**,
119/119 both ways. It is the command this project runs most, and it is 25% shorter.

### 3.0 What a small build is now made of

| | seconds |
|---|---|
| frontend (emit `.ll`) | 0.015 |
| `clang -O2 -c program.ll` | 0.052 |
| link | 0.14–0.18 |

The link is now the floor. `-fuse-ld=lld` is the obvious next lever and could not be measured here:
this host's LLVM ships no `lld`.

`L5` has no object cache, so its four columns should be equal; the spread across them is this
host's noise floor and is the right size to keep in mind when reading the rest. `T3`'s *cold*
number is not better than `L5`'s either — nothing about a first build changed, and the frontend it
did improve is 3.6% of one.

### 3.1 The compiler's own self-build

`tools/bootstrap.sh` is the path that builds the compiler, and its phases are:

| phase | seconds |
|---|---|
| frontend | 0.09 |
| `clang -O2 -c` on 1.80 MB of emitted IR | 0.96 |
| the seven toolchain sources, `-O2` (`aif_support.c` alone is 0.73) | 1.44 |
| link | ~0.3 |

**1.44 s of 2.67 s was recompiling seven C files that did not change**, in the loop this project
runs most. Both bootstrap scripts cache them now, on the same content key as §4 and with the same
`PRISMIO_OBJ_CACHE` knobs:

| | sequential | parallel |
|---|---|---|
| cache off (`PRISMIO_OBJ_CACHE=0`) | 2.67 | **2.09** |
| cold, populating an empty cache | 3.08 | 2.62 |
| **warm** | **1.58** | 1.58 |

**2.96 s before this session → 1.58 s warm, 46% off the compiler's own edit-rebuild loop.**
Populating costs ~0.5 s more than not caching at all, paid once per runtime edit.

The seven compiles are also issued in **parallel** now — they are seven independent translation
units writing seven distinct objects, so the only thing it changes is how long they take, and
`aif_support.c` at 0.73 s is the floor. That is worth 0.58 s on the *uncached* path, which is
exactly the path a session editing the runtime takes and the one the cache cannot help. A failed
job still fails the build and is named: verified by appending `this is not C;` to a copy of
`diagnostics.c` and watching `FAILED: cc diagnostics.c`, exit 1, no binary.

Two things about the key, because this is the one path whose contract is that an edit to
`runtime/*.c` reaches the next generation:

* **Every `runtime/*.h` goes into every entry.** A header changes what a `.c` compiles to without
  changing a byte of it. `embedded_sources.h` is one of them and is regenerated whenever any
  runtime source changes, so a session editing the runtime invalidates all seven and gets nothing
  from the cache — the right side to be wrong on. A session editing only `.psm` files, which is
  most of them, hits all seven.
* **`openssl` is preferred over `shasum`** for the hashing: `shasum` is a Perl script and eight
  invocations of it cost 0.178 s against 0.070 s. The remaining ~0.07 s is what the cache costs on
  a hit.

`run_bootstrap_cache_key_test` asserts the key is stable, per-source, and moves when either the
source or a header does — the last one verified discriminating by removing the header term and
watching exactly that assertion fire. **The PowerShell half is unverified**: there is no PowerShell
on the host this was written on, so `tools/bootstrap.ps1`'s copy of the cache has been written to
mirror the shell one and read, not run. CI's Windows leg is what will exercise it first.

A compiler built entirely from cached objects produces **byte-identical IR on every program** to
one built with `PRISMIO_OBJ_CACHE=0`. The binaries themselves differ by the linker's `LC_UUID`,
which is why the comparison is on IR (HANDOFF, 2026-08-17 second session §4).

## 4 · The toolchain object cache

`$TMPDIR/prismio-objcache/<role>-<16 hex>.obj`, keyed on FNV-1a over the role, the compile flags
and the source text — the same hash the runtime-staleness check uses, for the reason stated there:
mtimes move on a checkout and content does not.

* **Flags are in the key**, so a `--verify` object and a release object are different entries. An
  object built with `-DPRISMIO_AIF_VERIFY` linked into a release build puts half the allocations
  outside the ledger, which is the same failure the verify path already refuses an installed
  `runtime.lib` for.
* **Installed atomically**: compiled to a pid-qualified temporary and renamed. Two concurrent
  builds racing on one entry would otherwise link a half-written object — the profile race in
  `runWorkloadProfile` is the same mistake made the other way round.
* **The temporary is a sibling of the entry, and that is a fix rather than a detail.** The first
  version compiled next to the *output executable* and renamed into `$TMPDIR`. `rename()` cannot
  cross a filesystem, so on any host where those differ — `/tmp` as tmpfs on Linux, a build
  directory on a second volume — every install would have failed with `EXDEV`, the build would
  still have succeeded, and the cache would silently never have populated. Nothing local would
  have shown it: this Mac has one volume. `run_object_cache_test` now asserts the entry *appears*,
  rather than inferring it from a later hit.
* **`PRISMIO_OBJ_CACHE_DIR` is the directory, not a parent to append a name to.** The build driver
  appended `prismio-objcache` to it and the bootstrap scripts used it directly, so one variable
  meant two places while both reported hits. Found by the assertion above, which was looking in
  the directory the variable named and finding it empty.
* **`PRISMIO_OBJ_CACHE=0` bypasses it**, and says so in the trace, because "the cache was not
  consulted" and "the cache was consulted and had nothing" are different facts.
* **What the key does not cover: an in-place upgrade of clang.** Folding `clang --version` in was
  measured at 28 ms — 14% of what the cache saves — and was not worth paying on every build. The
  bypass above is the documented escape.

`run_object_cache_test` in the suite asserts cold-misses, warm-hits, that the linked program still
runs, that `--verify` keys separately, and that the bypass bypasses. It cannot assert the *content*
half of the key: a normal build unpacks the runtime embedded in the compiler binary rather than
reading `runtime/` from disk, so no test can edit what it compiles without a bootstrap.

## 5 · Pricing the per-module split, without building one

§2 says 76% of a cold build is `clang -O2` on one emitted module, and the fix everyone reaches for
is a compilation unit: one object per source file, so an edit recompiles one of them. That is a
large change — SPEC §7.5, REQUIREMENTS 10 and REQUIREMENTS 21 all need it — so it was priced first.

`llvm-split` cuts a module into *k* parts, which is what a per-file unit would produce, so both
halves of the trade are measurable today. Sequential, minimum of 2, `clang -O2 -c` per part.

| module | IR | unsplit | *k* | all parts | one part | rebuild speedup |
|---|---|---|---|---|---|---|
| `g1_particles` | 27 KB | 0.059 | 4 | 0.166 | 0.045 | 1.3× |
| | | | 8 | 0.293 | 0.041 | 1.4× |
| the compiler | 1.80 MB | 0.93 | 4 | 0.805 | 0.219 | 4.2× |
| | | 0.95 | 8 | 0.954 | 0.146 | 6.5× |
| synthetic 505 KB | 3.34 MB | 2.45 | 4 | 1.478 | 0.383 | 6.4× |
| | | 2.48 | 8 | **1.444** | 0.191 | **13×** |
| | | 2.47 | 16 | 1.621 | 0.109 | **23×** |

Three things fall out, and two of them were not what was expected.

**LLVM's `-O2` pipeline is superlinear in module size.** Splitting the 3.34 MB module four ways cuts
the *total* work by 40% — 2.45 s to 1.48 s — before any reuse, and before any parallelism. So a
per-module split is a **cold**-build win on a large program, not only an incremental one. That is
the same shape as §1's frontend result arriving one layer down.

**There is a crossover, and small programs are the wrong side of it.** Splitting `g1_particles`
eight ways costs 5× the total work: each part pays a fixed ~30–40 ms of process and pipeline
startup, and the module is 27 KB. A per-file unit therefore wants a floor — below roughly 100 KB of
IR, one module is cheaper than several.

**The runtime cost of losing cross-module optimisation is not measurable on this corpus.**

| program | *k* | unsplit | split | ratio |
|---|---|---|---|---|
| `xlang/g2` | 2 | 0.379 | 0.369 | 0.975× |
| | 4 | 0.381 | 0.374 | 0.981× |
| | 8 | 0.385 | 0.379 | 0.986× |
| `xlang/g6` | 8 | 0.734 | 0.745 | 1.014× |

All four are inside the per-program run-to-run bands recorded in RESULTS-xlang §0.1. There is a
mechanism behind it rather than luck: the hot code in these programs is `list_get`, `list_push` and
the allocator, which live in `lang_runtime.c` and have **always** been a separate object. Splitting
the program's own module does not move that boundary. A program whose hot loop is its own code
would have to be re-measured.

**What this does not price.** `llvm-split` partitions by global rather than by source file, so a
real implementation additionally pays for emitting a declaration set per file and for whatever the
partition does to string-literal and slot numbering (§2 is that failure in miniature). And the
frontend floor does not move: parse, sema and AIF are whole-program, so a rebuild of the 505 KB
project cannot go below **frontend 0.12 s + one part 0.19 s + link 0.18 s ≈ 0.5 s**, against 3.31 s
today. That is the number worth quoting for the feature: **~6.5× on a project of this size**, with
the crossover above saying it is worth nothing on a small one.

## 6 · Reproducing

```bash
python3 aif/evidence/compile_bench.py --compiler build/<gen> --baseline build/<old>   # §3
python3 tools/ir_snapshot.py --compiler build/<gen> --out /tmp/ir     # run alone (profile race)
python3 tools/ir_slot_diff.py /tmp/ir_before /tmp/ir_after            # tolerates slot renumbering
python3 tools/incremental_manifest.py --compiler build/<gen>          # INFERENCE 9's equality test
```

The scaling fixtures are generated, not committed: *N* functions each calling four earlier ones,
about 230 bytes per function. Any generator of that shape reproduces §1 — what matters is that the
declaration count and the call-site count grow together, because the cost was their product.
